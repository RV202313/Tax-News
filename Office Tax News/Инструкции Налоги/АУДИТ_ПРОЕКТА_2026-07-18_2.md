## 1. Итог аудита

Корень проекта не является Git-репозиторием. `postiz/.git` относится только к
upstream Postiz. Поэтому история и авторство проверялись по содержимому,
timestamps, SHA-256, журналам и runtime-артефактам; точную последовательность
перезаписанных файлов доказать нельзя.

Цепочка `ingest -> parse -> select -> digest -> approve -> publish` работает,
но дневные shortlist/digest являются mutable build outputs. На 18.07 они уже
содержат ноль позиций, тогда как два approved-релиза и sidecar доказывают
20 фактических доставок. Два честных backfill run-record проходят новый
независимый пересчёт. Будущий schema v3 теперь явно считает составом релиза
только approved + release-only sidecar; дневные outputs помечаются как
`context_only`, без недоказанной lineage.

Разделение source-of-truth подтверждено: корневой каталог — факт
использования/размещения и главный дедуп-каталог; SQLite — кандидаты/статусы
и производный индекс; JSONL — факт доставки; run-record — конкретный релиз;
pipeline log — только журнал. Для Telegram ID 155–174 sidecar и каталог дают
20/20, дублей `(release, slug, delivery)` нет.

Scheduler-of-record по актуальным owner-docs — одна owner-managed Cowork-задача
`academy-news-daily` в 08:00 Europe/Amsterdam. `launchctl print` не нашёл daily,
court и editorial-listener; plist являются шаблонами. Наличие самой desktop
Cowork-задачи из файлов/инструментов macOS не проверяется. Court-run 07:00
системным scheduler не обеспечен.

Судебный runtime-срез неполон: в реестре 39 Rechtspraak и 24 RAS; полный
текст есть для 5/39 Rechtspraak и 0/24 RAS, завершённый анализ — 0/63.
Исторический RAS raw содержит 22/24 явно датированных строк вне окна. Без
массового сетевого добора это не подменялось. Будущий court receipt теперь
пересчитывает registry/full-text/analysis coverage и ставит `complete=false` при gap.

Telethon-session не занята по `lsof`, но её фактические права — `0644`.
Клиенты теперь fail-closed требуют `0600` или строже, advisory lock и чистый
`lsof`; публикатор повторяет `get_me()` перед каждым `send_file`.

## 3. Исправления и причины

1. `court_morning_run.py` теперь пишет preliminary receipt до тяжёлого
   этапа и после него пересчитывает registry/full-text/analysis coverage
   для Rechtspraak и RAS. `complete=true` невозможен при пропуске источника,
   полного текста или анализа.
2. `publish_batch.py` создаёт run-record schema v3: approved/sidecar — авторитетны,
   daily outputs — только контекст. `--verify-run-record` пересчитывает
   SHA-256, размеры и delivery coverage; повторное использование run-id
   сначала верифицирует весь receipt. Изменение approved после старта execute
   явно блокирует создание receipt.
3. `session_guard.py` блокирует открытие отсутствующей или доступной
   группе/прочим session. Сохранены advisory lock и fail-closed `lsof`;
   `get_me()` повторяется перед каждой Telegram-отправкой.
4. Production-path docs синхронизированы: scheduler-of-record, source-of-truth,
   court receipt, run-record schema v3, Telethon ownership и RAS `browserURL` из
   `config/sources.yaml` (сейчас 9223, не исторический пример 9222).

Существующие backfill run-records, дневные shortlist/digest, court registry/raw и
session-файл не переписывались. Это сохраняет историческую честность и
чужие изменения.

## 6. Оставшиеся blocker/risk и решения владельца

1. **Telethon-session mode 0644.** Код теперь блокирует сбор/отправку до
   исправления прав. Владельцу нужно выполнить `chmod 600` для точного
   существующего session-файла. Аудит не изменял файл вне рабочей папки.
2. **Court-run 18.07 незавершён.** Нужен отдельно разрешённый targeted
   production rerun с Chrome на URL из config. До него исторические raw/registry
   нельзя помечать complete или ретроспективно чистить.
3. **Court scheduler 07:00.** Решение владельца: явный шаг существующей Cowork-задачи
   или один court LaunchAgent; не оба. Desktop Cowork также нужно вручную
   подтвердить как реальную scheduler-of-record 08:00.
4. **Историческая lineage 09:00/13:00 утрачена.** Решение сохранено:
   не реконструировать mutable shortlist/digest/manifests; опираться на честные
   backfill approved+sidecar и обязательный schema v3 для будущих execute.
5. **Внешний Telethon-клиент может игнорировать advisory lock.** `lsof`
   снижает риск, но остаётся race после preflight. Для полной изоляции нужно
   решение владельца об отдельной авторизованной collector-session; аудит её не создавал.
6. Postiz production acceptance, KPI `>=30%` в трёх реальных выпусках, GCP и
   принятый риск неротированных credentials остаются без изменений.
