# Отчёт по проверке endpoints (2026-07-02)

Проверка выполнена ТОЛЬКО через `mcp__workspace__web_fetch` (raw curl/wget заблокирован
в этом окружении). Сырые ответы сохранены в `pipeline/raw/probe/{source_id}.txt`.

Общий вывод по инструменту: `web_fetch` показывает как текст HTML и
`application/atom+xml`, но рендерит `[binary data]` для `application/xml` (plain)
и `application/rss+xml` — то есть **классический RSS 2.0 и «сырой» XML практически
бесполезны через web_fetch**, даже если сервер честно отдаёт контент. Также
обнаружено: повторяющиеся query-параметры (`date=A&date=B`) молча схлопываются —
выживает только первое вхождение.

## 1. nl_rechtspraak — data.rechtspraak.nl (Open Data, Uitspraken)

**Пробовали:** список `zoeken` с `date=`, с двумя `date=`, с `subject=belastingrecht`
(в нескольких вариантах кодирования и вместе/без `type=uitspraak`), контентный
endpoint `content?id=`.

**Что реально работает:**
- `http://data.rechtspraak.nl/uitspraken/zoeken?date=YYYY-MM-DD&max=N` — стабильно
  работает. Формат: **Atom 1.0** (`Content-Type: application/atom+xml`), редиректит
  http→https. Пример: `date=2026-06-29&max=10` вернул `Aantal gevonden ECLI's: 271`
  и полные `<entry>` с `id` (ECLI), `title`, `summary` (аннотация ~200-400 симв.),
  `updated` (ISO8601), `link rel="alternate"` на человекочитаемую страницу
  `uitspraken.rechtspraak.nl/details?id=...`.
- Поля на элемент: **ECLI, заголовок (суд+дата+номер дела), краткое summary,
  дата обновления, ссылка на HTML-страницу**. Даты — точные, «свежесть»
  подтверждена (последние записи на 2026-07-02 присутствуют при запросе на этот
  день).

**Что НЕ работает / квирки:**
- **Двойной `date=FROM&date=TO`** (официальный способ задать диапазон дат) —
  второй параметр молча пропадает при фактическом запросе через web_fetch
  (видно по итоговому redirect URL). Реально долетает только `date=FROM`
  (один календарный день за вызов). **Практическое следствие: нужно перебирать
  окно по дням отдельными вызовами**, а не одним запросом с диапазоном.
- **`subject=http://psi.rechtspraak.nl/rechtsgebied#belastingrecht`** (фильтр по
  правовой области «налоговое право») — во ВСЕХ протестированных вариантах
  (с `type=uitspraak` и без, с узким и с ~6-месячным окном, с `#belastingrecht`
  и без фрагмента вовсе) стабильно возвращает **`Aantal gevonden ECLI's: 0`**.
  Не удалось подтвердить рабочий синтаксис фильтра. Возможные причины: неверный
  URI в актуальном value-list, изменение API, либо реальный ноль совпадений в
  комбинации с иным багом. **Не считать эту фильтрацию рабочей.**
- **`content?id=ECLI:...`** (полный текст решения) — отдаёт `Content-Type:
  application/xml`, и web_fetch показывает **`[binary data]`** — текст решения
  не извлечь через web_fetch. И с `&return=DOC`, и без — тот же результат.
- Официальный список `Rechtsgebieden` (`http://data.rechtspraak.nl/Waardelijst/
  Rechtsgebieden`) тоже вернул `[binary data]` — не удалось свериться со
  «словарём» правовых областей напрямую.

**Практический воркэраунд для пайплайна:** тянуть список по датам (один день —
один вызов, `date={DATE}&max=200&return=DOC`), без `subject`-фильтра, и
отбирать налоговые дела клиентским скорингом по ключевым словам в
`title`/`summary` (это и так заложено в `topics.yaml`/`select_news.py`).
Полный текст решения не тянуть через web_fetch — если нужен полный текст,
альтернатива на будущее: HTML-страница `uitspraken.rechtspraak.nl/details?id=...`
(не проверялась в этом прогоне, кандидат для отдельного теста).

**Свежесть:** отлично — записи за сам день запроса присутствуют (проверено на
2026-06-29 и опосредованно на 2026-07-01/02 через широкий `max=300` запрос).

## 2. ru_ras — ras.arbitr.ru (Банк решений арбитражных судов)

**Пробовали:** `https://ras.arbitr.ru/` (только эта точка, без обхода антибота
по прямому указанию задачи).

**Результат:** пустое тело ответа — просто эхо URL, ни заголовка, ни контента,
ни явной HTTP-ошибки. Ожидаемо: JS-рендеринг + антибот-защита, web_fetch не
видит контент вообще.

**Статус:** для автопоиска использовать Chrome/UI, не частый прямой HTTP.
Обычная страница `ras.arbitr.ru` работает в браузере; прямой поиск через
`/Ras/Search` без браузерного контекста/капчи может давать 451/капчу. Для
конвейера это не «мертвый» источник, а обязательный ручной/Chrome-добор до
SELECT с паузами между запросами.

## 3. ru_garant — garant.ru (правовые новости)

**Пробовали:** `/rss/`, `/rss/all/`, спекулятивный `/ia/aggregator/rss/`,
главная страница, категорийная страница-агрегатор «Налоги и бухучёт».

**Что НЕ работает:**
- Все три RSS-подобных пути (`/rss/`, `/rss/all/`, `/ia/aggregator/rss/`) —
  пустое тело через web_fetch. Ссылка `/rss/` присутствует в навигации живого
  сайта (значит RSS существует в принципе), но по факту прямой фетч этой ссылки
  не отдаёт контент в этом окружении.

**Что работает:**
- **Главная страница** (`https://www.garant.ru/`) — HTML, `charset=windows-1251`
  (корректно определена и раскодирована web_fetch), полностью читаемый
  markdown-конвертированный вывод: навигация, блок новостей, ссылка на RSS в
  футере/шапке.
- **Категорийная страница-агрегатор `/ia/aggregator/nalogi-i-buhuchet/`**
  («Налоги и бухучёт») — HTML, тот же windows-1251, чистый список новостей:
  заголовок (ссылка на `/news/{id}/`) + короткий тизер под каждым заголовком,
  плюс навигация по остальным рубрикам (`sudebnaya-practica`, `biznes`,
  `practica`, `trud` и т.д. — могут пригодиться как доп. источники).
  Явной даты публикации рядом с каждым заголовком в выбранном фрагменте не
  обнаружено (даты на странице относятся скорее к анонсам семинаров) — для
  точной даты публикации нужно открывать конкретную статью.

**Статус:** RSS НЕ подтверждён рабочим через web_fetch. **HTML-агрегатор —
рабочий, рекомендуемый способ** (`parser: html_links`, не `rss`).

**Свежесть:** страница живая (общий баннер событий на «6 июля 2026» и т.п.),
но без точных pubDate на уровне списка — свежесть отдельных новостей не
подтверждена напрямую в этом пробеге.

## 4. intl_regfollower — regfollower.com

**Пробовали:** `/feed/` (без www и с www), главная страница.

**Что НЕ работает:**
- `https://regfollower.com/feed/` — отдаёт `Content-Type: application/rss+xml`,
  но web_fetch показывает **`[binary data]`** (та же проблема, что и с
  rechtspraak content и taxence feed).
- `https://www.regfollower.com/feed/` (вариант с www) — пустое тело.

**Что работает:**
- **Главная страница** (`https://regfollower.com/`, БЕЗ www) — HTML, WordPress
  6.9.4, отлично читаемая, с богатой рубрикацией (TAX: Corporate/Pillar Two/
  Transfer Pricing/Personal/Tax Policy/Anti-avoidance/VAT/Other Taxes; TRADE;
  AGREEMENTS: Tax Treaties/Free Trade/TIEAs; REGIONS; TAX FORUMS). Список
  новостей: заголовок (ссылка), дата («09 June, 2026» формат), абзац-тизер,
  флаг страны, «Read More». Плюс тематические мини-блоки (Pillar Two,
  Corporate Tax, Transfer Pricing, Tax Policy, Tax Treaty) с отдельными
  короткими списками — удобно для точечного отбора по теме.

**Квирк свежести:** самые новые записи на главной датированы **«09 June, 2026»**
— это ~3.5 недели раньше даты проверки (2026-07-02). На странице также виден
статичный баннер «Wednesday, June 10, 2026» (явно кэш-артефакт, не реальный
день недели). Похоже на закэшированный снапшот на стороне сайта/CDN, отданный
именно этому фетчу. **Свежесть требует переподтверждения на живом прогоне** —
не закладывать предположение о материалах «за сегодня» без повторной проверки.

**Статус:** WORKS (только главная страница; RSS существует, но нечитаем через
web_fetch).

## 5. nl_fd — fd.nl (Het Financieele Dagblad, платный)

**Пробовали:** `/rss`, главная, `/economie`, `/tags/belasting`.

**Результат:** **все четыре пути вернули пустое тело** — просто эхо URL, ни
заголовка, ни тизера, ни meta. Не HTTP-ошибка, а именно пустой ответ — похоже
на антибот/пейволл-гейт, блокирующий небраузерные запросы полностью (в отличие
от некоторых пейволлов, которые всё же отдают открытые заголовки/анонсы).
Обход не предпринимался.

**Статус:** DEAD через web_fetch. Ни одного байта полезного контента, даже
открытых заголовков. Рекомендация: если fd.nl всё же нужен — только `chrome`
(ручной/Claude-in-Chrome заход), как и `ru_ras`. Endpoint для web_fetch в
конфиг не включать за отсутствием вообще какого-либо результата.

## 7. nl_taxence — taxence.nl (Lefebvre Sdu, WordPress)

**Пробовали:** `/feed/` (со слэшем), `/feed` (без слэша), главная страница.

**Что НЕ работает / квирки:**
- **`/feed/`** (со слэшем) — явный отказ: **`"Web fetch was not allowed."`**
  Это отдельный тип ошибки (не таймаут, не пустое тело) — похоже на явную
  политику блокировки именно этого пути+слэша.
- **`/feed`** (без слэша) — уже НЕ блокируется, отдаёт `Content-Type:
  application/rss+xml`, но контент всё равно **`[binary data]`** — та же
  проблема рендеринга не-atom XML, что у regfollower и rechtspraak.

**Что работает — лучший источник из всех семи:**
- **`https://www.taxence.nl/`** — HTML, WordPress 7.0, полностью читаемый,
  **самые свежие материалы из всех проверенных источников**: заголовки
  датированы **сегодняшним днём, 2 juli 2026** (день проверки!), включая
  прямые судебные материалы:
  - «Koopsom nieuwe woning telt niet als schuld in box 3» (Rechtbank
    Gelderland) — 2 juli 2026
  - «Nabetaling ziektewetuitkering belast in jaar van ontvangst» (Hof
    's-Hertogenbosch) — 2 juli 2026
  - «Certificaten aandelen tellen mee voor bedrijfsopvolging» (Gerechtshof
    Amsterdam) — 1 juli 2026
  Поля на элемент: заголовок (ссылка), дата, автор (ссылка на профиль или
  «redactie»), абзац-тизер («... lees verder»), картинка. Пагинация до
  страницы 2446 — большой активный архив (`/page/N/`).

**Статус:** WORKS (главная страница — образцовый пример; `/feed` технически
резолвится, но контент нечитаем через web_fetch; `/feed/` со слэшем явно
заблокирован).

**Общие квирки инструмента web_fetch, влияющие на все источники:**
1. `application/atom+xml` рендерится как текст; `application/xml` (plain) и
   `application/rss+xml` рендерятся как `[binary data]` — RSS 2.0 и сырой XML
   практически бесполезны через web_fetch, даже если сервер их честно отдаёт.
2. Повторяющиеся query-параметры (`?date=A&date=B`) — второе вхождение молча
   пропадает; для диапазонов дат нужен цикл по отдельным вызовам.
3. Пустое тело ответа (просто эхо URL) — частый патторн у антибот/пейволл
   защит (ras.arbitr.ru, fd.nl, garant.ru/rss/) — отличается от явной ошибки
   («Web fetch was not allowed» видели только у taxence.nl/feed/) и от
   таймаута (видели у некоторых длинных query-строк на data.rechtspraak.nl,
   не воспроизвелось стабильно после упрощения запроса).
4. Кириллица (garant.ru, windows-1251) декодируется корректно самим
   инструментом — квирк только в моём терминальном выводе при чтении файла,
   не в самих данных.
5. У двух источников (`intl_regfollower`, `nl_taxlive`) новейшие записи на
   главной странице оказались на 2-3.5 недели старше даты проверки — похоже
   на закэшированный снапшот, отданный именно этому фетчу. Рекомендуется
   переподтвердить актуальность на первом живом прогоне пайплайна, не
   закладывать это как постоянное свойство источника.
