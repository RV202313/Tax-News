## 0. Как читать и исполнять это задание

Это не инструкция «сделай сразу всё», а последовательный план из фаз. Правила исполнения:

1. **Порядок фаз жёсткий.** Фаза N начинается только после приёмки фазы N−1 владельцем. Владелец подтвердил приоритет: «всё по порядку» — сначала навести порядок, затем источники, затем публикация.
2. **Роли.** Claude (Opus/Fable/Sonnet по типу работы) отвечает за детерминированное ядро, рефакторинг, конфиги, документацию и проверку. Codex — за редакционный слой и реальную публикацию. Разделение труда детально — в разделе 7. Пожелание владельца по моделям: концепция — Fable, код — Opus, вспомогательное — Sonnet.
3. **Ничего не ломать в бою.** Действующий поток (Codex → Telethon → редакционный Telegram-чат, 3×10 постов/день) продолжает работать всё время рефакторинга. Переключение на новые механизмы — только после приёмки и «сухого прогона».
4. **Каждое изменение фиксировать** в журналах проекта: `News Claude/log/pipeline_log.md` (ядро Claude), `ЖУРНАЛ_ПРОГОНОВ_CODEX.md` (Codex). Изменения процесса синхронно вносить в `News Claude/PROCESS.md` и `МАНУАЛ_ПОДГОТОВКИ_НОВОСТЕЙ_CODEX.md`, чтобы инструкция не расходилась с практикой.
5. **Проверять на реальной машине.** Черновик задания составлен по снапшоту папки; часть выводов требует перепроверки на месте. Первый шаг Фазы 0 — это подтвердить факты.

## 2. Целевая картина (что должно получиться)

Единый, воспроизводимый и наблюдаемый конвейер, который:

1. **Автоматически собирает** новости международного/трансграничного налогообложения из четырёх типов источников:
   - российские суды (ras.arbitr.ru и, по возможности, ВС/Минфин/ФНС);
   - голландские суды (rechtspraak.nl) — стабильно;
   - профильные Telegram-каналы (переиспользуя уже существующий Telethon-монитор);
   - веб/агрегаторы (garant, taxence, regfollower, belastingdienst и т.д.) и, опционально, сайты юрфирм из методики Academy Legal News.
2. **Готовит** редакционно-качественные материалы по действующему протоколу (7-дневное окно, первичный источник, «Почему это важно», обязательная иллюстрация, оба хештега, дисклеймер для судебных).
3. **Публикует** через **Postiz как дополнительный хаб рядом с существующим Telegram-потоком** (Telegram-редпоток Codex сохраняется как есть; Postiz подключается для остальных каналов — VK, LinkedIn, сайт, email — и, при желании, дублирует Telegram). Вместо одноразовых `beps_batch_*.py` — **один переиспользуемый движок публикации**, читающий посты из файла данных.
4. **Не плодит мусор**, не дублирует работу отбора, хранит состояние надёжно и не содержит утёкших секретов.

Починка — **перестать использовать web_fetch и перейти на официальный публичный Open Data API rechtspraak по прямому HTTP** (`requests` в конвейере уже есть):
1. **Поиск:** `GET https://data.rechtspraak.nl/uitspraken/zoeken` → Atom XML. Параметры: `date=YYYY-MM-DD` (можно указать дважды — диапазон, окно 7 дней) либо `modified=YYYY-MM-DDTHH:MM:SS`; `subject=<URI рехтсгебид>` для фильтра «belastingrecht» (точный URI взять из справочника `https://data.rechtspraak.nl/Waardelijst/Rechtsgebieden`, ориентир — `http://psi.rechtspraak.nl/rechtsgebied#bestuursrecht_belastingrecht`); `type=Uitspraak`; `return=DOC` (только с доступным текстом); `sort=DESC`; `max` (≤1000).
2. **Полный текст решения:** `GET https://data.rechtspraak.nl/uitspraken/content?id=ECLI:NL:...` → XML (Dublin Core/RDF + текст решения). Парсить локально (`lxml`/`ElementTree`), **не** через web_fetch. В утреннем судебном прогоне тянуть тексты **всех** ECLI дня, заносить их в реестр `court_analysis/court_decisions.csv`, а в `court_analysis/rechtspraak` оставлять только substantive решения по международному налогообложению.
3. Сервер просит не слать параллельные запросы и фильтровать — ходить последовательно, с паузой.
4. Заменить regex-парсер `rechtspraak_atom` на нормальный XML-парсер; фильтр по теме теперь делает сам API (`subject`), клиентский скоринг оставить как второй слой.
*DoD:* rechtspraak собирается прямым HTTP без provenance-сбоев; полный текст решений доступен и парсится; фильтр belastingrecht работает на стороне API; ручной Chrome-добор больше не нужен.

**2c. Telegram как источник — КАК ЧИНИТЬ.**
Первопричина: сбор из Telegram уже есть (Telethon-монитор `Academy Network/Телеграм`, ~16 налоговых каналов, аккаунт Academy_of_BEPS, `track_engagement`), но он делает AI-дайджесты «в сторону» и не подаётся в конвейер. Починка:
1. Collector-шаг `collect_telegram.py` на той же Telethon-сессии: за последние 7 дней вытащить сообщения каналов группы `tax_channels_digest` из `config.yaml`.
2. Нормализовать в item’ы (канал, msg_id, дата, текст, извлечённые ссылки на первоисточники, просмотры/реакции) → `pipeline/inbox`; keyword-фильтр по `topics.yaml`. Вовлечённость (реакции/просмотры относительно среднего по каналу) — как доп. сигнал ранжирования в `select_news`.
3. Пометка: Telegram-посты часто **вторичны** → метить как `lead`; первоисточник Codex подтверждает отдельно (по протоколу факты берутся только из первичного источника).
4. Добавить Telegram-источники в `config/sources.yaml` (`method: telethon`); дедуп по ссылке/акту/теме с остальными.
*DoD:* налоговые Telegram-каналы дают item’ы-лиды в inbox автоматически, с метриками вовлечённости, без отдельного «дайджеста в сторону».

**2d. Веб/агрегаторы.** Рабочие HTML-источники сохранить как есть (garant, taxence, regfollower, belastingdienst, ФНС) с учётом квирков из `ENDPOINTS_REPORT.md`. Мониторинг сайтов юрфирм (методика Academy Legal News + «Проект Ирины С») **сейчас не включаем** (см. раздел 8, решение 2) — вернёмся отдельной фазой позже.

**Definition of Done фазы:** все четыре типа источников дают item’ы в `inbox` автоматически (или с явным залогированным ручным шагом там, где иначе нельзя); дедуп между источниками работает; дайджест содержит RU-суды и Telegram-лиды.

### Фаза 3 — Публикация через Postiz рядом с Telegram (Codex ведёт, Claude — движок/конфиг)

Прескриптивно, «как чинить публикацию»:
1. **Убрать `beps_batch_*.py` как класс.** Первопричина мусора: контент захардкожен в каждый одноразовый скрипт. Починка — один движок `publish_batch.py`, который читает посты из файла данных `pipeline/approved/{выпуск}.json` (поля: `title`, `text`, `hashtags`, `image_path`, `channels`, `scheduled_at`), генерит карточки (вынести `build_card` из beps_batch в модуль `cards.py`), публикует и пишет результат в `ОПУБЛИКОВАННЫЕ_НОВОСТИ.md` + состояние. **Ноль хардкода контента** — контент только в json. Старые `beps_batch_*.py` удалить/заархивировать.
2. **Подключить Postiz (транспорт — localhost, см. решение 1 раздела 8).** Codex работает на маке, поэтому `localhost:4007` ему доступен и облако сейчас не нужно. Discovery `GET /api/public/v1/integrations` → записать реальные `postiz_integration_id` в `config/postiz.yaml` (сейчас пустые). Публикация `POST /api/public/v1/posts` строго по контракту `scripts/postiz_publish.md` (Authorization = сырой ключ без Bearer).
3. **Каналы — рядом, без дублей.** Telegram-редпоток Codex остаётся через Telethon как есть; в Postiz его **не дублировать** (иначе двойной постинг — см. решение 3). Postiz настраивается на VK, LinkedIn (по умолчанию `draft`), сайт (WordPress через `publishers.publish_wordpress`), email. Правило «публикация только после явного „да“ по каждому посту» сохраняется.
4. **Секреты (P0):** Postiz API-ключ и Telegram API — в `.env`, не в git; ротировать утёкшие в `docker-compose.cloud.yaml` ключи.

**Definition of Done:** ни одного нового `beps_batch_*.py`; выпуск публикуется одним движком из json; в `config/postiz.yaml` заполнены integration_id; Postiz публикует хотя бы в один дополнительный канал в проде; Telegram-поток не сломан и не задублирован.

### Фаза 4 — Приёмка

Полный «сухой прогон» одного дня end-to-end на тестовых каналах: сбор из всех четырёх источников → отбор/дедуп → редакционная подготовка → публикация через Postiz + Telegram → запись состояния. Офлайн-тесты, проверка отсутствия утечек, ревью журналов. Отчёт владельцу.

## 8. Принятые решения (рекомендации Claude, приняты по умолчанию)

Чтобы исполнитель не ждал и не плодил вопросы, по каждому пункту зафиксировано решение с обоснованием. Если владелец не возражает — работать по ним. Возражения принимаются на старте Фазы 0.

1. **Postiz — остаёмся на localhost, облако откладываем.** Обоснование: реальную публикацию делает Codex, а он работает на маке и `localhost:4007` ему доступен — «невидимость localhost из песочницы» касается только Claude-в-облаке, а не боевого потока. Облачный стек (Temporal/Elasticsearch) — лишняя операционная нагрузка и источник утечек. Утёкшие секреты ротировать в любом случае. *К облаку вернуться, только если понадобится публиковать из среды без мака.*
2. **Сайты юрфирм (Academy Legal News + «Проект Ирины С») — сейчас НЕ включаем.** Обоснование: это большой отдельный слой (site discovery + классификация + браузерный fallback); подключать его до стабилизации четырёх основных источников — распыление. Идеи и код методики переиспользуем позже, отдельной фазой. Пока — только инвентаризировать в Фазе 0.
3. **Telegram в Postiz НЕ дублируем.** Обоснование: Telegram-редпоток уже надёжно работает через Telethon с ручным редакционным контролем; дублирование через Postiz даст двойной постинг и рассинхрон. Postiz — только не-Telegram каналы (VK, LinkedIn, сайт, email).
4. **Внешний диск Elements и «Проект Ирины С» — инвентарь в Фазе 0.** После подключения папок Claude сам их каталогизирует и предложит решение «переиспользовать / доработать / вывести из эксплуатации»; отдельного решения владельца до инвентаря не требуется.

5. **ВС РФ и Минфин — включаем в Фазу 2 сразу (решение владельца от 2026-07-17, высокий приоритет).** Развилки больше нет: российский блок Фазы 2 = ras.arbitr.ru + ВС РФ + Минфин + ФНС, все с рецептами в пункте 2a. Открытых вопросов, блокирующих старт, не осталось.
